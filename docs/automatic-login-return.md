# Возврат из браузера после входа VK ID

## Реализация

1. Приложение создаёт `state` и PKCE verifier в памяти и открывает VK ID.
2. VK ID возвращает браузер на зарегистрированный `https://153-51-114-47.sslip.io/callback`.
3. Страница из `web/login-return/` передаёт `state`, `code`, `device_id` либо отказ `error` на фиксированный `vkm://auth/callback`.
4. Зарегистрированная схема `vkm` доставляется через `QFileOpenEvent`; приложение поднимает окно и передаёт ответ текущей попытке входа. Ссылки `vkm://chat/...` продолжают работать.
5. Приложение проверяет маршрут и state, затем однократно обменивает код локально с PKCE. В запросе обмена остаётся исходный HTTPS `redirect_uri`.

Возврат не принимает userinfo, порт, fragment, другой host/path, повторные и несовместимые параметры. Неверный callback не уничтожает действующую попытку. Повтор принятого callback во время или после обмена не создаёт второй запрос. Отмена, отказ VK ID и таймер в пять минут завершают попытку; после перезапуска её нужно начать заново. Проверяется и `state` в ответе обмена токена. Неопределённый результат сетевого обмена требует нового входа, старый код автоматически не отправляется снова.

В окне входа видны ожидание браузера и обмен токена, есть отмена и «Вставить ссылку вручную». Страница делает автоматическую попытку возврата и оставляет кнопку «Вернуться в приложение». После очистки адресной строки резервный HTTPS callback остаётся в раскрываемом поле на странице — его можно вставить в приложение. Verifier и токены через страницу не проходят; сторонних скриптов и сетевого обмена на ней нет.

## Ошибки Messages API

Успешный VK ID login сохраняет сессию, но доступ к Messages API проверяется отдельно. При недоступном `messages.getDiff` (коды 3/7/15/27 либо конкретный текст отказа по типу профиля) выполняется `messages.getConversations`. Для ошибки типа профиля не предполагается недокументированный числовой код.

Если публичное чтение тоже недоступно, клиент сохраняет сессию, останавливает синхронизацию и Long Poll, приостанавливает передачи и не отправляет новые запросы `messages.*`. В интерфейсе остаётся понятное ограничение с названием метода и числовым кодом. Повторная вставка callback не даёт дополнительных прав. Новый вход или обновление токена заново проверяют доступ. Произвольный текст ответа VK и `request_params` в диагностике не показываются.

## Состояние сервера

28 октября 2026 страница развёрнута по SSH на `vsafin@153.51.114.47`. Сервер использует Caddy 2.6.2. Файлы установлены в `/var/www/vkm-login-return/20261028-auth-return`, конфигурация — `/etc/caddy/Caddyfile`. Проверка `caddy validate` прошла, сервис успешно перезагружен и активен.

Публичные `/callback`, `/login-return/callback.js` и `/login-return/style.css` отвечают HTTP 200, имеют правильные Content-Type, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` и CSP. ETag и Last-Modified удалены; SHA-256 всех трёх опубликованных файлов совпадают с файлами репозитория. Дополнительно в Safari проверены HTTPS-загрузка страницы и выполнение callback.js без параметров авторизации: показано ожидаемое сообщение о необходимости начать вход в приложении. Для этих маршрутов задан `skip_log` (название директивы в Caddy 2.6.2); access log в существующей конфигурации не был включён.

Исходная конфигурация и страница сохранены в `/var/backups/vkm-login-return/20261028-auth-return/`. Прежний `/var/www/vk-auth/index.html` не изменён и продолжает обслуживать остальные адреса. Для отката: восстановить `Caddyfile` из этого резервного каталога в `/etc/caddy/Caddyfile`, выполнить `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile` и `systemctl reload caddy` с sudo. Реальный VK ID login и доступ конкретной сессии к сообщениям требуют проверки пользователем в новой сборке.

## Развёртывание

Сначала установить новую сборку macOS, затем обновить страницу. App ID `54850913` и HTTPS redirect в кабинете VK менять не нужно.

1. Сохранить копии действующей страницы и конфигурации сервера.
2. Скопировать только `index.html`, `callback.js`, `style.css` из `web/login-return/` в `/var/www/vkm-login-return` (или согласованный каталог с соответствующим изменением конфигурации).
3. В существующий блок домена Caddy добавить маршруты из `web/login-return/Caddyfile.example`, заменив прежний обработчик `/callback`. Пример использует `skip_log`, проверенный на установленном Caddy 2.6.2; начиная с 2.8 директива называется `log_skip`. Остальные маршруты и TLS сохраняются. Для nginx есть отдельный `nginx.conf.example`.
4. Проверить конфигурацию командой `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`, затем применить штатным способом запуска сервера. Убедиться, что query callback не записывается в access/error/debug-журналы Caddy и внешнего прокси; пример отключает access log этих маршрутов.
5. Проверить HTTP 200 для `/callback`, `/login-return/callback.js`, `/login-return/style.css`, правильные Content-Type, `no-store`, `no-referrer`, CSP и отсутствие сторонних запросов. Не использовать реальные коды авторизации для проверки сервера.
6. Выполнить новый вход в Safari и Chrome: автоматический возврат, разрешение браузера и кнопка возврата, затем отдельно ручная вставка из резервного поля. Запускать один экземпляр приложения; доставка URL между несколькими одновременно запущенными копиями не гарантируется.

Для отката восстановить прежнюю страницу и конфигурацию: ручной HTTPS callback остаётся совместимым.

## Проверки в репозитории

`protocol-tests` проверяет PKCE и точные адреса возврата. `messenger-tests` проверяет доставку `QFileOpenEvent`, активацию окна, исходный HTTPS redirect, кодирование параметров, дубли через оба пути, неверный state, отказ, отмену, истечение времени, перезапуск и сетевую ошибку. Интеграционные сценарии покрывают публичный API после отказа getDiff, ограничение профиля, сохранение сессии и отсутствие повторных сетевых запросов. `login-return-tests` запускается через Node и проверяет параметры, кодирование, автоматический переход, заблокированный переход и ручной резервный URL.

Проверено 28 октября 2026: сборка Release, все 10 наборов CTest, 16 проверок страницы в Node, подпись упакованного macOS bundle и `--self-check` (QML, SQLite, SVG/WebP/GIF, Opus). Схема `vkm` присутствует в Info.plist.

Тесты используют синтетические данные и подставной API; живой вход и разрешения конкретной сессии VK они не подтверждают. Коды авторизации из переписки в файлы не включены.
